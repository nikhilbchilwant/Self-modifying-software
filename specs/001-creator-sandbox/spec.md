- Q: How should the sandbox interface handle invalid code or compiler/runtime errors generated by the AI backend? → A: Use a verification loop where compilation errors are fed back to the Pi AI backend for auto-fixing before presenting to the user.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Live Experimentation in Sandbox Mode (Priority: P1)

Users can activate a "Sandbox Mode" to experiment with modifying the UI and logic of the application by typing natural language prompts, seeing the results instantly without page reload.

**Why this priority**: Core value proposition of the sandbox mode, allowing interactive and zero-downtime evolution.

**Independent Test**: Verify that the sandbox mode can be entered, a user can submit a text prompt to modify the UI (e.g. "change theme to green"), the UI updates instantly, and the state (e.g. text input in a form) is preserved.

**Acceptance Scenarios**:

1. **Given** the user is on the main application dashboard, **When** they click "Enter Sandbox Mode", **Then** the application enters Sandbox Mode with a clear visual indicator.
2. **Given** the application is in Sandbox Mode, **When** the user enters a prompt to change the layout (e.g., "Add a conversion rate dial") and submits, **Then** the app UI hot-reloads to show the new dial, while preserving any existing entered data in nearby forms.
3. **Given** the application is in Sandbox Mode, **When** the user clicks "Exit Sandbox Mode", **Then** the application discards all live changes and returns to the default production app state.

---

### User Story 2 - Submitting Feature Requests with Visuals (Priority: P2)

Users who are satisfied with their sandbox modifications can submit them as a feature request with a screenshot and code diff.

**Why this priority**: Crucial feedback loop that connects user experimentation to actionable developer tasks.

**Independent Test**: Verify that clicking the "Submit Feedback" button successfully captures the screenshot and diff, and transmits it to the destination.

**Acceptance Scenarios**:

1. **Given** the user has modified the UI in Sandbox Mode, **When** they click "Submit Feature Request", **Then** the system captures a visual snapshot of the current state and generates a code diff.
2. **Given** the snapshot and diff are generated, **When** the request is submitted, **Then** a feedback submission is saved to the local file system (in a designated feedback folder) and the user receives a confirmation message.

---

### User Story 3 - Sandbox Mode Access (Priority: P3)

The Sandbox Mode is accessible to all users of the application without restriction, encouraging active experimentation.

**Why this priority**: Supports the demo environment design where anyone can experiment with the application.

**Independent Test**: Verify that any user visiting the application is presented with the "Enter Sandbox Mode" option and can access it.

**Acceptance Scenarios**:

1. **Given** any user views the application, **When** they look at the interface, **Then** they see the "Enter Sandbox Mode" option.
2. **Given** any user enters the application, **When** they click "Enter Sandbox Mode", **Then** they are successfully granted access to the sandbox environment.

### Edge Cases

- What happens when the AI generates invalid syntax or compilation errors? The backend verification loop detects it, sends the logs back to Pi, and retries/auto-fixes it.
- How does the system handle an unresolvable code error in the verification loop? It reverts the sandbox code to the last known working state and shows a warning overlay in the frontend.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide a toggle/button to enter and exit the Sandbox Mode environment.
- **FR-002**: System MUST track sandbox modifications in a temporary registry isolated from the production environment.
- **FR-003**: System MUST discard all sandbox registry changes immediately when exiting Sandbox Mode.
- **FR-004**: System MUST inject dynamic UI and logic modifications into the active DOM without resetting application state (state-preserving hot reloading).
- **FR-005**: System MUST capture a high-fidelity visual snapshot (PNG format) of the modified workspace when submitting feedback.
- **FR-006**: System MUST generate a structured code diff representing the changes made during the sandbox session compared to the baseline code.
- **FR-007**: System MUST save the screenshot and code diff package to a local feedback directory.
- **FR-008**: System MUST baseline code changes against the initial codebase state at the moment the user entered Sandbox Mode.
- **FR-009**: AI modifications MUST be compiled and verified by the backend using a feedback loop (errors sent back to AI for auto-fixing) before HMR injection.
- **FR-010**: Frontend UI MUST utilize pre-installed `recharts` and `lucide-react` libraries for visualization and layout.
- **FR-011**: The dashboard theme MUST strictly align with the Apple Mac Keynote light theme (sleek, minimalist off-white/gray canvas, charcoal/dark-gray text, crisp thin borders, and clean primary accents).

### Key Entities *(include if feature involves data)*

- **Sandbox Session**: Represents the active experimental session, including session ID, start time, temporary registry of modifications, and status (Active, Exited).
- **Feature Request**: The feedback submission containing a unique request ID, timestamp, user ID, screenshot artifact (PNG), code diff artifact, and optional user description.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: UI hot-reloading completes in under 1.5 seconds from user prompt submission (excluding backend verification retries).
- **SC-002**: Visual snapshotting captures 100% of visible DOM elements in the workspace within 2 seconds of clicking submit feedback.
- **SC-003**: 100% of user-entered input values (e.g. text fields, dropdown selections) remain intact after sandbox hot reloading.
- **SC-004**: Exit Sandbox Mode successfully discards all experimental changes and restores the application to production state in under 1 second.

## Assumptions

- Sandbox Mode changes do not write back to the production repository or database during the session.
- Users are accessing the application via a modern web browser that supports HMR and canvas screenshotting capabilities.
- The AI backend is capable of generating valid component/logic modifications from natural language prompts.
